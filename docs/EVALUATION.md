# Σύστημα Δοκιμών και Αξιολόγησης

## 1. Σκοπός

Με το σύστημα αξιολόγησης θέλουμε να ελέγχουμε πώς συμπεριφέρεται συνολικά το σύστημα των έξυπνων ανελκυστήρων, τόσο σε συνηθισμένες συνθήκες όσο και όταν προκύπτουν προβλήματα.

Η λογική είναι απλή: δημιουργούμε δοκιμαστικά αιτήματα επιβατών, τα στέλνουμε στο Κεντρικό Σύστημα και παρακολουθούμε τα γεγονότα που αναφέρουν οι ανελκυστήρες. Έπειτα χρησιμοποιούμε αυτά τα δεδομένα για να υπολογίσουμε, μεταξύ άλλων, πόση ώρα περιμένουν οι επιβάτες, πόσο διαρκεί η διαδρομή τους και πόσα αιτήματα εξυπηρετήθηκαν.

Συγκεκριμένα, το υποσύστημα αναλαμβάνει:

- Δημιουργία σεναρίων λειτουργίας.
- Δημιουργία εικονικών αιτημάτων χρηστών.
- Αποστολή αιτημάτων στο Κεντρικό Σύστημα.
- Λήψη γεγονότων από τους ανελκυστήρες.
- Καταγραφή της εξέλιξης κάθε αιτήματος.
- Υπολογισμός μετρικών απόδοσης.
- Καταγραφή σφαλμάτων και γεγονότων ασφαλείας.
- Εμφάνιση των τελικών αποτελεσμάτων.

## 2. Επικοινωνία με τα άλλα συστήματα

Η βασική επικοινωνία μεταξύ των υποσυστημάτων έχει την εξής μορφή:

```text
Σύστημα Αξιολόγησης
        |
        | POST /requests
        v
Κεντρικό Σύστημα
        |
        | POST /stops
        v
Σύστημα Ελέγχου Ανελκυστήρα
        |
        | POST /events
        v
Σύστημα Αξιολόγησης
```

Στην πράξη, η αξιολόγηση στέλνει αιτήματα στο Κεντρικό, μπορεί να ζητήσει την κατάσταση των ανελκυστήρων και λαμβάνει τα γεγονότα που αυτοί στέλνουν. Με το `request_id` αντιστοιχίζει κάθε γεγονός στο σωστό αίτημα, ώστε οι τελικές μετρήσεις να βασίζονται στην πορεία του συγκεκριμένου επιβάτη.


## 3. Εκκίνηση

Το πρόγραμμα θα ξεκινά από τη γραμμή εντολών. Για παράδειγμα, μπορούμε να το εκτελέσουμε ως εξής:

Παράδειγμα:

```bash
java -jar evaluation-system.jar \
  --port 8300 \
  --central-url http://localhost:3000
```

Οι παράμετροι που έχουμε προβλέψει είναι οι παρακάτω:

| Παράμετρος | Παράδειγμα | Σημασία |
|---|---|---|
| `--port` | `8300` | Θύρα του Συστήματος Αξιολόγησης |
| `--central-url` | `http://localhost:3000` | Διεύθυνση Κεντρικού Συστήματος |
| `--scenario` | `uniform` | Σενάριο δοκιμής |
| `--requests` | `100` | Πλήθος αιτημάτων |
| `--duration-seconds` | `300` | Διάρκεια δοκιμής |
| `--seed` | `42` | Τιμή επαναληψιμότητας |

Ένα πιο ολοκληρωμένο παράδειγμα, αυτή τη φορά με σενάριο πρωινής αιχμής:

```bash
java -jar evaluation-system.jar \
  --port 8300 \
  --central-url http://localhost:3000 \
  --scenario morning_rush \
  --requests 100 \
  --duration-seconds 300 \
  --seed 42
```


## 4. Σενάρια αξιολόγησης

Για να μη δοκιμάζουμε τον αλγόριθμο μόνο με έναν τύπο κίνησης, έχουμε ορίσει τρία σενάρια. Το πρώτο προσομοιώνει τυχαίες μετακινήσεις, ενώ τα άλλα δύο τις ώρες πρωινής προσέλευσης και απογευματινής αποχώρησης.

### 4.1 Κοινοί κανόνες

Σε κάθε εκτέλεση ορίζουμε τις εξής παραμέτρους:

- `floors`: πλήθος ορόφων (3–200).
- `request_count`: πλήθος αιτημάτων (θετικός ακέραιος).
- `duration_seconds`: διάρκεια παραγωγής αιτημάτων (θετικός ακέραιος).
- `seed`: αρχική τιμή γεννήτριας τυχαίων αριθμών.

Οι όροφοι αριθμούνται από `0` έως `floors - 1`.

Ανεξάρτητα από το σενάριο, πρέπει να ισχύουν τα εξής:

- Ο όροφος αφετηρίας είναι έγκυρος.
- Ο όροφος προορισμού είναι έγκυρος.
- Αφετηρία και προορισμός διαφέρουν.
- Κάθε αίτημα έχει μοναδικό αναγνωριστικό.
- Τα αιτήματα παράγονται εντός της διάρκειας δοκιμής.

Για την αρχική εκδοχή προτείνουμε οι χρόνοι αποστολής να επιλέγονται τυχαία και ομοιόμορφα μέσα στη διάρκεια του run. Έπειτα τα αιτήματα μπαίνουν σε χρονολογική σειρά. Αυτός ο κανόνας χρειάζεται επιβεβαίωση από την ομάδα πριν θεωρηθεί οριστικός.

### 4.2 Uniform

Στο `uniform` θέλουμε να δούμε πώς τα πηγαίνει το σύστημα όταν οι μετακινήσεις γίνονται τυχαία σε όλο το κτίριο, χωρίς κάποιος όροφος ή κάποια κατεύθυνση να έχει προτεραιότητα.

Για κάθε αίτημα:

1. Επιλέγεται τυχαία ο όροφος αφετηρίας από `0` έως `N-1`.
2. Επιλέγεται τυχαία διαφορετικός όροφος προορισμού από τους υπόλοιπους `N-1` ορόφους.
3. Το αίτημα αποκτά χρόνο αποστολής εντός της διάρκειας δοκιμής.

Κάθε έγκυρος όροφος έχει ίση πιθανότητα επιλογής ως αφετηρία. Για δεδομένη αφετηρία, κάθε διαφορετικός προορισμός είναι ισοπίθανος.

Παράδειγμα:

```text
3 → 12
8 → 1
0 → 6
```

### 4.3 Morning rush

Το `morning_rush` προσομοιώνει την ώρα που ο κόσμος μπαίνει στο κτίριο, για παράδειγμα το πρωί σε ένα κτίριο γραφείων.

Για κάθε αίτημα:

1. Η αφετηρία ορίζεται στον όροφο `0`.
2. Ο προορισμός επιλέγεται τυχαία από τους ορόφους `1` έως `N-1`.
3. Το αίτημα αποκτά χρόνο αποστολής εντός της διάρκειας δοκιμής.

Στην απλή εκδοχή του σεναρίου όλοι ξεκινούν από το ισόγειο και οι προορισμοί μοιράζονται ισοπίθανα στους υπόλοιπους ορόφους.

Παράδειγμα:

```text
0 → 5
0 → 12
0 → 8
```

### 4.4 Evening rush

Το `evening_rush` εξετάζει την αντίστροφη κατάσταση: οι επιβάτες αποχωρούν από το κτίριο και κατευθύνονται προς το ισόγειο.

Για κάθε αίτημα:

1. Η αφετηρία επιλέγεται τυχαία από τους ορόφους `1` έως `N-1`.
2. Ο προορισμός ορίζεται στον όροφο `0`.
3. Το αίτημα αποκτά χρόνο αποστολής εντός της διάρκειας δοκιμής.

Στην πρώτη εκδοχή όλοι έχουν προορισμό το ισόγειο, ενώ η αφετηρία επιλέγεται ισοπίθανα από τους υπόλοιπους ορόφους.

Παράδειγμα:

```text
15 → 0
7 → 0
12 → 0
```

### 4.5 Επαναληψιμότητα

Θέλουμε να μπορούμε να επαναλάβουμε ακριβώς το ίδιο σύνολο αιτημάτων όταν χρησιμοποιούμε τις ίδιες ρυθμίσεις.

Με ίδιο σενάριο, seed, πλήθος ορόφων, πλήθος αιτημάτων και διάρκεια, παράγεται ακριβώς η ίδια ακολουθία αιτημάτων και σχετικών χρόνων αποστολής.

Η γεννήτρια τυχαίων αριθμών αρχικοποιείται μία φορά ανά run. Τα αιτήματα ταξινομούνται βάσει του σχετικού χρόνου αποστολής, με σταθερή σειρά σε περίπτωση ισοπαλίας.

Αυτό αφορά τα αιτήματα που παράγουμε, όχι την εγγύηση ότι κάθε run θα έχει ίδιους χρόνους εξυπηρέτησης. Οι χρόνοι εξαρτώνται και από την κατάσταση των ανελκυστήρων.

### 4.6 Προαιρετικά μελλοντικά σενάρια

Σε επόμενη φάση θα μπορούσαμε να δοκιμάσουμε επίσης:

- Πολλά ταυτόχρονα αιτήματα.
- Χρονικά συγκεντρωμένη αιχμή.
- Ανελκυστήρας εκτός λειτουργίας.
- Βλάβη θύρας.
- Υπέρβαση βάρους.
- Διακοπή ρεύματος.
- Κατάσταση έκτακτης ανάγκης.
- Απότομη πτώση πίεσης σε υδραυλικό ανελκυστήρα.

Αυτές οι περιπτώσεις δεν είναι μέσα στον στόχο της πρώτης λειτουργικής έκδοσης.


## 5. Επαναληψιμότητα

Οι κανόνες παραγωγής αιτημάτων περιγράφονται στην ενότητα 4.5. Εδώ κρατάμε τον λόγο που τους χρειαζόμαστε: με ίδιο σενάριο, `seed` και ίδιες παραμέτρους δημιουργούμε το ίδιο φορτίο δοκιμής. Έτσι μπορούμε να συγκρίνουμε δύο εκδόσεις του αλγορίθμου χωρίς να αλλάζουν στο μεταξύ τα αιτήματα.


## 6. Καταστάσεις ενός run

```java
public enum RunStatus {
    CREATED,
    RUNNING,
    COMPLETED,
    FAILED,
    CANCELLED
}
```

| Κατάσταση | Σημασία |
|---|---|
| `CREATED` | Το run δημιουργήθηκε |
| `RUNNING` | Η δοκιμή εκτελείται |
| `COMPLETED` | Η δοκιμή ολοκληρώθηκε |
| `FAILED` | Παρουσιάστηκε σοβαρό σφάλμα |
| `CANCELLED` | Η δοκιμή ακυρώθηκε |

Για να ξεχωρίζουμε τις εκτελέσεις μεταξύ τους, κάθε run παίρνει δικό του `run_id`.

Παράδειγμα:

```text
run-001
```


## 7. Καταστάσεις αιτήματος

```java
public enum RequestStatus {
    CREATED,
    SENT,
    ASSIGNED,
    PICKED_UP,
    COMPLETED,
    FAILED
}
```

Για κάθε αίτημα κρατάμε τα βασικά στοιχεία και τις χρονικές στιγμές που μας χρειάζονται:

- `request_id`
- `source_floor`
- `destination_floor`
- `assigned_elevator_id`
- `created_at`
- `assigned_at`
- `pickup_at`
- `dropoff_at`
- `status`

## 8. Μετρικές

### Χρόνος ανάθεσης

```text
assignment_time = assigned_at - created_at
```

### Χρόνος αναμονής

```text
waiting_time = pickup_at - created_at
```

### Χρόνος διαδρομής

```text
travel_time = dropoff_at - pickup_at
```

### Συνολικός χρόνος εξυπηρέτησης

```text
total_service_time = dropoff_at - created_at
```

### Μέσος χρόνος αναμονής

```text
average_waiting_time =
άθροισμα χρόνων αναμονής / ολοκληρωμένα αιτήματα
```

### Μέσος χρόνος διαδρομής

```text
average_travel_time =
άθροισμα χρόνων διαδρομής / ολοκληρωμένα αιτήματα
```

### Ποσοστό επιτυχίας

```text
success_rate =
ολοκληρωμένα αιτήματα / συνολικά αιτήματα × 100
```

### Throughput

```text
throughput =
ολοκληρωμένα αιτήματα / διάρκεια δοκιμής σε λεπτά
```

Εκτός από τους παραπάνω δείκτες, μας ενδιαφέρει να καταγράφουμε και:

- Μέγιστος χρόνος αναμονής.
- Πλήθος αποτυχημένων αιτημάτων.
- Αιτήματα ανά ανελκυστήρα.
- Στάσεις ανά ανελκυστήρα.
- Όροφοι που διένυσε κάθε ανελκυστήρας.
- Γεγονότα ασφαλείας.

### 8.1 Αριθμητικά παραδείγματα υπολογισμού KPIs

Οι τύποι από μόνοι τους δεν αρκούν για τον έλεγχο του κώδικα. Γι’ αυτό κρατάμε μερικά παραδείγματα με γνωστές τιμές, ώστε να ξέρουμε τι αποτέλεσμα πρέπει να δώσει ο υπολογισμός και να το ελέγξουμε αργότερα με JUnit.

#### Παράδειγμα 1: Υπολογισμός χρόνων ενός αιτήματος

Ας πάρουμε ένα απλό αίτημα από τον 2ο στον 8ο όροφο. Υποθέτουμε ότι έχουμε καταγράψει τους παρακάτω χρόνους:

| Γεγονός | Χρονική στιγμή |
|---|---|
| `created_at` | 10:00:00 |
| `assigned_at` | 10:00:02 |
| `pickup_at` | 10:00:15 |
| `dropoff_at` | 10:00:35 |

Από αυτές τις χρονικές στιγμές προκύπτουν:

- Χρόνος ανάθεσης: 2 δευτερόλεπτα (2.000 ms).
- Χρόνος αναμονής: 15 δευτερόλεπτα (15.000 ms).
- Χρόνος διαδρομής: 20 δευτερόλεπτα (20.000 ms).
- Συνολικός χρόνος εξυπηρέτησης: 35 δευτερόλεπτα (35.000 ms).

Προσοχή: τα 2 δευτερόλεπτα της ανάθεσης περιλαμβάνονται ήδη στα 15 δευτερόλεπτα αναμονής. Δεν τα προσθέτουμε ξανά στον συνολικό χρόνο.

#### Παράδειγμα 2: Υπολογισμός συνολικών KPIs

Τώρα ας θεωρήσουμε ένα run διάρκειας 300 δευτερολέπτων. Στείλαμε 5 αιτήματα: τα 4 ολοκληρώθηκαν και το ένα απέτυχε.

| Request | Waiting time | Travel time | Status |
|---|---:|---:|---|
| R1 | 10 s | 20 s | COMPLETED |
| R2 | 15 s | 25 s | COMPLETED |
| R3 | 20 s | 30 s | COMPLETED |
| R4 | 15 s | 25 s | COMPLETED |
| R5 | — | — | FAILED |

**Μέσος χρόνος αναμονής:**

```text
(10 + 15 + 20 + 15) / 4 = 15 s
```

**Μέσος χρόνος διαδρομής:**

```text
(20 + 25 + 30 + 25) / 4 = 25 s
```

**Μέγιστος χρόνος αναμονής:**

```text
max(10, 15, 20, 15) = 20 s
```

**Ποσοστό επιτυχίας:**

```text
4 / 5 × 100 = 80%
```

**Throughput:**

```text
4 / (300 / 60) = 0.8 requests/min
```

Το αποτυχημένο αίτημα δεν μπαίνει στον μέσο χρόνο αναμονής ή διαδρομής, αφού δεν έχουμε πλήρη στοιχεία εξυπηρέτησης. Μετρά όμως στο σύνολο των αιτημάτων, άρα επηρεάζει το ποσοστό επιτυχίας.

#### Παράδειγμα 3: Έλεγχος οριακών περιπτώσεων

- Εάν δεν υπάρχει κανένα ολοκληρωμένο αίτημα, οι μέσοι χρόνοι δεν υπολογίζονται και προτείνεται να επιστρέφονται ως `null`, ώστε να αποφεύγεται η διαίρεση με το μηδέν.
- Εάν ολοκληρωθούν όλα τα αιτήματα, το ποσοστό επιτυχίας είναι 100%.
- Εάν αποτύχουν όλα τα αιτήματα, το ποσοστό επιτυχίας είναι 0%.
- Αρνητικοί χρόνοι απορρίπτονται ως άκυρα δεδομένα.
- Ένα διπλό event δεν πρέπει να επηρεάζει δεύτερη φορά τις μετρικές.
- Event `DROPOFF_COMPLETED` χωρίς προηγούμενο `PICKUP_COMPLETED` απορρίπτεται.

Για τους μέσους χρόνους χωρίς διαθέσιμα δεδομένα προτείνουμε `null`. Θα το επιβεβαιώσουμε όταν κλειδώσει το κοινό API.

#### Παράδειγμα 4: Αναμενόμενα αποτελέσματα για JUnit tests

Για τα δεδομένα του Παραδείγματος 2, ο `MetricsCalculator` πρέπει να επιστρέφει:

```text
completed_requests = 4
failed_requests = 1
average_waiting_time_ms = 15000
maximum_waiting_time_ms = 20000
average_travel_time_ms = 25000
success_rate_percent = 80.0
throughput_requests_per_minute = 0.8
```

Οι αριθμοί αυτοί είναι ενδεικτικοί και θα χρησιμοποιηθούν για tests· δεν προέρχονται από πραγματική προσομοίωση.


## 9. POST /runs

Με το συγκεκριμένο endpoint ζητάμε να ξεκινήσει μια νέα εκτέλεση δοκιμής.

```http
POST http://localhost:8300/runs
Content-Type: application/json
```

Request:

```json
{
  "scenario": "uniform",
  "request_count": 100,
  "duration_seconds": 300,
  "seed": 42,
  "floors": 20,
  "elevators": 4
}
```

Απάντηση:

```http
202 Accepted
```

```json
{
  "run_id": "run-001",
  "status": "RUNNING",
  "scenario": "uniform",
  "request_count": 100,
  "seed": 42
}
```

Άγνωστο scenario:

```http
400 Bad Request
```

```json
{
  "error": "unknown scenario"
}
```

Αν το Κεντρικό Σύστημα δεν είναι διαθέσιμο:

```http
503 Service Unavailable
```

```json
{
  "error": "central system is unavailable"
}
```


## 10. POST /events

Σε αυτό το endpoint οι ανελκυστήρες αναφέρουν γεγονότα, ώστε η αξιολόγηση να παρακολουθεί την εξέλιξη των αιτημάτων.

```http
POST http://localhost:8300/events
Content-Type: application/json
```

Παράδειγμα:

```json
{
  "run_id": "run-001",
  "timestamp": "2026-11-23T13:30:04Z",
  "elevator_id": "C",
  "request_id": 41,
  "event": "ARRIVED",
  "floor": 7
}
```

Απάντηση:

```http
202 Accepted
```

```json
{
  "accepted": true
}
```

Άγνωστο `run_id`:

```http
404 Not Found
```

```json
{
  "error": "run not found"
}
```

## 12. Αιτήματα προς το Κεντρικό Σύστημα

Για να δοκιμάσει το Κεντρικό Σύστημα, η αξιολόγηση στέλνει αιτήματα όπως το παρακάτω:

```http
POST http://localhost:3000/requests
Content-Type: application/json
```

Παράδειγμα:

```json
{
  "source_floor": 2,
  "destination_floor": 7,
  "request_id": 41,
  "source": "EVALUATION"
}
```

Απάντηση Κεντρικού:

```json
{
  "request_id": 41,
  "elevator_id": "A",
  "status": "ASSIGNED"
}
```

Από την απάντηση κρατάμε ποιος ανελκυστήρας ανέλαβε το αίτημα και πότε έγινε η ανάθεση.


## 13. Γεγονότα ανελκυστήρα

Τα γεγονότα που έχουμε προβλέψει μέχρι στιγμής είναι:

| Event | Σημασία |
|---|---|
| `STOP_ASSIGNED` | Προστέθηκε στάση |
| `MOVEMENT_STARTED` | Ξεκίνησε η κίνηση |
| `FLOOR_PASSED` | Πέρασε από έναν όροφο |
| `PICKUP_COMPLETED` | Παραλήφθηκε ο χρήστης |
| `DROPOFF_COMPLETED` | Ολοκληρώθηκε η διαδρομή |
| `DOORS_OPENED` | Άνοιξαν οι θύρες |
| `DOORS_CLOSED` | Έκλεισαν οι θύρες |
| `STOPPED` | Σταμάτησε ο ανελκυστήρας |
| `RESUMED` | Επανήλθε σε λειτουργία |
| `OVERLOAD` | Εντοπίστηκε υπερφόρτωση |
| `DOOR_BLOCKED` | Εντοπίστηκε εμπόδιο |
| `EMERGENCY` | Ενεργοποιήθηκε έκτακτη ανάγκη |
| `POWER_FAILURE` | Διακόπηκε η τροφοδοσία |
| `OUT_OF_SERVICE` | Τέθηκε εκτός λειτουργίας |
| `HYDRAULIC_PRESSURE_DROP` | Εντοπίστηκε πτώση πίεσης |

Το `PICKUP_COMPLETED` χρησιμοποιείται για τον χρόνο αναμονής και το `DROPOFF_COMPLETED` για τον χρόνο διαδρομής.

## 16. Έλεγχος λανθασμένων δεδομένων

Δεν αρκεί να λειτουργούν τα σωστά αιτήματα. Πρέπει να απορρίπτονται και οι παρακάτω περιπτώσεις:

- Άγνωστο scenario.
- Αρνητικό ή μηδενικό πλήθος αιτημάτων.
- Άκυρο `run_id`.
- Άκυρο `request_id`.
- Άγνωστο event.
- Όροφο εκτός ορίων.
- Ίδιο όροφο αφετηρίας και προορισμού.
- `DROPOFF_COMPLETED` πριν από `PICKUP_COMPLETED`.
- Χρονική στιγμή ολοκλήρωσης πριν από τη δημιουργία του αιτήματος.

Κοινή μορφή σφάλματος:

```json
{
  "error": "invalid event sequence"
}
```

## 18. Προδιαγραφές JUnit tests

Τα JUnit tests θα μας βοηθήσουν να ελέγχουμε αυτόματα ότι ο κώδικας κάνει αυτά που περιγράφει ο σχεδιασμός.

Για να είναι εύκολο να εντοπίζουμε λάθη, κάθε test θα έχει συγκεκριμένα δεδομένα εισόδου και γνωστό αναμενόμενο αποτέλεσμα. Τα βασικά tests θα τρέχουν και χωρίς ενεργό Κεντρικό Σύστημα ή ανελκυστήρες.

### 18.1 Υποχρεωτικά tests πρώτης έκδοσης

**TEST-01: Uniform request generation**

Είσοδος:

- Scenario: `uniform`
- Floors: `20`
- Request count: `100`
- Duration: `300` seconds
- Seed: `42`

Αναμενόμενα αποτελέσματα:

- Παράγονται ακριβώς 100 αιτήματα.
- Κάθε όροφος ανήκει στο διάστημα `[0, 19]`.
- Για κάθε αίτημα `source_floor != destination_floor`.
- Κάθε αίτημα έχει μοναδικό αναγνωριστικό.
- Οι σχετικοί χρόνοι αποστολής βρίσκονται μέσα στη διάρκεια δοκιμής.

**TEST-02: Seed reproducibility**

Είσοδος:

- Δύο ανεξάρτητες εκτελέσεις του `uniform`.
- Ίδιο seed (`42`).
- Ίδιο πλήθος ορόφων (`20`).
- Ίδιο πλήθος αιτημάτων (`100`).
- Ίδια διάρκεια (`300` seconds).

Αναμενόμενα αποτελέσματα:

- Παράγονται οι ίδιες αφετηρίες.
- Παράγονται οι ίδιοι προορισμοί.
- Διατηρείται η ίδια σειρά αιτημάτων.
- Οι σχετικοί χρόνοι αποστολής είναι ίδιοι.

Εδώ συγκρίνουμε τα παραγόμενα αιτήματα και τους σχετικούς χρόνους τους, όχι την πραγματική διάρκεια εκτέλεσης του προγράμματος.

**TEST-03: Waiting time calculation**

Είσοδος:

```text
created_at = 10:00:00
pickup_at  = 10:00:15
```

Αναμενόμενο αποτέλεσμα:

```text
waiting_time_ms = 15000
```

Χρησιμοποιούμε τις παραπάνω σταθερές χρονικές στιγμές, όχι την τρέχουσα ώρα του υπολογιστή, για να βγαίνει πάντα το ίδιο αποτέλεσμα.

### 18.2 Πρόσθετα tests σεναρίων

**TEST-04: Morning rush**

Για κάθε αίτημα:

- `source_floor == 0`.
- `destination_floor >= 1`.
- `destination_floor < floors`.

**TEST-05: Evening rush**

Για κάθε αίτημα:

- `source_floor >= 1`.
- `source_floor < floors`.
- `destination_floor == 0`.

### 18.3 Πρόσθετα tests μετρικών

**TEST-06: Travel time**

```text
pickup_at  = 10:00:15
dropoff_at = 10:00:35

Expected: travel_time_ms = 20000
```

**TEST-07: Success rate**

```text
total_requests = 5
completed_requests = 4
failed_requests = 1

Expected: success_rate_percent = 80.0
```

**TEST-08: Average waiting time**

Για τέσσερα ολοκληρωμένα αιτήματα με χρόνους αναμονής 10, 15, 20 και 15 δευτερόλεπτα:

```text
Expected: average_waiting_time_ms = 15000
```

### 18.4 Έλεγχοι οριακών περιπτώσεων

Όταν προχωρήσει η υλοποίηση, θα προσθέσουμε ελέγχους και για τις εξής περιπτώσεις:

- Απόρριψη μη έγκυρου ορόφου.
- Απόρριψη ίδιου ορόφου αφετηρίας και προορισμού.
- Απόρριψη μηδενικού ή αρνητικού πλήθους αιτημάτων.
- Απόρριψη άγνωστου σεναρίου.
- Απόρριψη `DROPOFF_COMPLETED` πριν από `PICKUP_COMPLETED`.
- Αποφυγή διπλής καταμέτρησης του ίδιου event.
- Αποφυγή διαίρεσης με το μηδέν όταν δεν υπάρχουν ολοκληρωμένα αιτήματα.

### 18.5 Εκτέλεση δοκιμών

Για να τρέξουμε τα tests, χρησιμοποιούμε την εντολή Maven:

```bash
mvn test
```

Για την πρώτη έκδοση στοχεύουμε στα TEST-01, TEST-02 και TEST-03, μόλις υπάρχουν οι αντίστοιχες λειτουργίες στον κώδικα.

Τα υπόλοιπα tests θα προστεθούν σταδιακά, παράλληλα με τα επόμενα σενάρια και τις μετρικές.

Σε αυτό το στάδιο περιγράφουμε τα tests που θέλουμε να υπάρχουν. Δεν σημαίνει ότι έχουν ήδη γραφτεί ή εκτελεστεί.


## 19. Αυτόνομη ανάπτυξη

Δεν χρειάζεται να περιμένουμε να ολοκληρωθεί το Κεντρικό Σύστημα για να ξεκινήσουμε τις δοκιμές της αξιολόγησης.

Μπορούμε αρχικά να χρησιμοποιήσουμε έναν `FakeCentralClient` που επιστρέφει μια προκαθορισμένη ανάθεση:

```java
public class FakeCentralClient implements CentralClient {

    @Override
    public AssignmentResponse sendRequest(GeneratedRequest request) {
        return new AssignmentResponse(
                request.getRequestId(),
                "A",
                "ASSIGNED"
        );
    }
}
```

Έτσι μπορούμε να δοκιμάσουμε ξεχωριστά:

- Τη δημιουργία των σεναρίων.
- Την επαναληψιμότητα του seed.
- Την αποθήκευση των events.
- Τον υπολογισμό των μετρικών.
- Τα REST endpoints.
- Την εμφάνιση των αποτελεσμάτων.

Όταν είναι έτοιμη η σύνδεση με το Κεντρικό, θα αντικαταστήσουμε το fake με έναν `HttpCentralClient`.

## 21. Περιορισμοί αρχικής έκδοσης

Στην αρχή θα υπάρχουν οι εξής περιορισμοί:

- Τα δεδομένα αποθηκεύονται μόνο στη μνήμη.
- Τα αποτελέσματα χάνονται όταν σταματήσει το πρόγραμμα.
- Δεν υπάρχει γραφική διεπαφή.
- Οι χρόνοι προέρχονται από προσομοίωση.
- Δεν γίνεται πραγματική μέτρηση κατανάλωσης ενέργειας.
- Μπορεί αρχικά να υποστηρίζεται μόνο το `uniform`.
- Ορισμένα events μπορούν να δημιουργούνται τεχνητά για δοκιμές.
- Τα σενάρια βλαβών μπορούν να προστεθούν αργότερα.


## 22. Κριτήρια ολοκλήρωσης

Θα θεωρήσουμε ότι η πρώτη λειτουργική έκδοση είναι έτοιμη όταν:

- Ξεκινά από τη γραμμή εντολών.

- Δημιουργεί ένα run.
- Δημιουργεί έγκυρα αιτήματα.
- Το ίδιο seed δίνει τα ίδια αιτήματα.

- Συνδέει τα events με τα σωστά αιτήματα.
- Υπολογίζει χρόνο αναμονής.
- Υπολογίζει χρόνο διαδρομής.
- Υπολογίζει ποσοστό επιτυχίας.
- Επιστρέφει αποτελέσματα σε JSON.
- Αντιμετωπίζει άκυρα δεδομένα.
- Περνούν τα βασικά JUnit tests.
- Το project μεταγλωττίζεται με Maven.
- Η υλοποίηση συμφωνεί με το `API.md`.
